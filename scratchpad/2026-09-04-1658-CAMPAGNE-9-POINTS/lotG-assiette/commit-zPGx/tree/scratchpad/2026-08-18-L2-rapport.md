## Ce qui est fait

### 1. La table

`supabase/migrations/20260818180000_a_session_is_a_fact_not_an_energy.sql` — créneau réservé,
aucun autre horodatage utilisé.

```sql
student_activity_sessions(
  id, user_id → auth.users ON DELETE CASCADE,
  local_date date not null,
  kind       text not null check in ('daily_movement','strength','cardio','recovery','mobility'),
  duration_min integer      check (>= 1 and <= 600),      -- nullable: déclarée, jamais devinée
  intensity  text           check in ('easy','moderate','hard'),  -- nullable, même raison
  source     text not null check in ('app','chat'),
  created_at timestamptz not null default now()
)
```

**⛔ Aucune colonne d'énergie.** La raison est écrite en tête de la migration, avec ses nombres
(déficit visé 400-500 kcal/j ; erreur d'une dépense déclarée ±30-50 %, soit 150-250 kcal sur une
séance annoncée à 500 ⇒ la soustraire **augmente** l'incertitude). Le paragraphe s'adresse
nommément à la prochaine session, qui voudra ajouter la colonne.

**Le vocabulaire n'est pas inventé.** `kind` = `ACTIVITY_EMPHASES` (`activity_stance.ts`), mot pour
mot. Les trois autres listes du dépôt ont été écartées avec leur motif :

| Liste | Où | Pourquoi pas elle |
|---|---|---|
| `PRACTICE_KINDS` | `daily_practices.ts` | le SUJET d'une pratique du coach ; `movement` y est 1 sujet sur 7 |
| `ACTIVITY_LEVELS` | `tokens.ts` | un TRAIT DURABLE de la personne, pas un événement daté |
| `ACTIVITY_CLASS` | `tokens.ts` | la classe d'un ENGAGEMENT, avec exemption R6 explicite |
| **`ACTIVITY_EMPHASES`** | `activity_stance.ts` | ✅ la seule qui décrive DE QUOI est faite une séance |

`activity_stance.ts` **n'est pas modifié** (il appartient à une autre session, et il n'est pas dans
HEAD). La liste est donc **recopiée** dans un module neuf, avec sa condition de retrait écrite :
importer dès que `activity_stance.ts` est dans HEAD, ou poser un test d'égalité des deux listes.

### 2. Les trois pièges des tables neuves

**(a) Privilèges.** `revoke all from public` **puis** `from anon, authenticated` — les deux, parce
que le premier laisse `anon` debout. Prouvé par lecture, pas par intention :

```
$ psql -c "select r.rolname||' '||v.p||' = '||has_table_privilege(...)"
 anon DELETE = false          authenticated DELETE = true
 anon INSERT = false          authenticated INSERT = true
 anon SELECT = false          authenticated SELECT = true
 anon TRUNCATE = false        authenticated TRUNCATE = false
 anon UPDATE = false          authenticated UPDATE = false
```

`TRUNCATE` est vérifié séparément parce qu'il **échappe à RLS** : une policy propriétaire-seul ne
l'arrête pas. `UPDATE` n'est pas accordé — une séance mal saisie se retire et se re-logue ; aucun
écran ne « corrige » une séance, et le dépôt a déjà payé un `update` qui touche 0 ligne en silence.

Le bloc de contrôle porte aussi **les cas passants** (`authenticated` PEUT lire et écrire ses
propres séances, `service_role` PEUT lire) — sans eux, sept refus verts ne prouveraient que « tout
est bloqué », c'est-à-dire une table morte déguisée en table sûre.

**(b) RLS ≠ `.eq(user_id)`.** Les policies sont propriétaire-seul (select / insert / delete), et
`loadWeekFacts` porte **quand même** son `.eq("user_id", userId)`. Ce n'est pas de la redondance :
le chargeur tourne en `service_role` dans le cron, où RLS ne s'applique pas. La preuve
correspondante est dans `2026-08-18-L2-preuve-consommateur.ts` — une séance semée chez un AUTRE
élève dans la même fenêtre, et le recalcul rend toujours `sessions: 3`.

**(c) Cycle de vie RGPD.** La table est réclamée **dans le même lot que sa migration** :
- `supabase/functions/account-export-v1/index.ts` — `SCOPE.studentActivitySessions`, un
  `fetchKeelRows`, et la clé `mon_plan.json → seances_dactivite` ;
- `supabase/functions/purge-deleted-accounts/index.ts` — un `delete().eq("user_id", …)` **explicite**
  malgré la FK CASCADE, exactement comme `inbound_dedup` : « ne rien laisser dépendre d'un
  ON DELETE qu'on n'a pas relu » ;
- `supabase/functions/keel_gdpr_lifecycle_test.ts` — entrée dans le contrat `PIVOT_TABLES`, seed,
  assertion de vocabulaire propre (`mobility`, comme `whatsapp_button` pour les taps du soir), et
  une assertion supplémentaire : **aucune clé d'énergie dans les lignes exportées**.

### 3. Le consommateur

`_shared/keel/activity_session.ts` (**neuf**, pur) — vocabulaire, parseurs, `summarizeWeekActivity`,
`parseWeekActivity`, `renderWeekActivityFact`.

`_shared/keel/week_review.ts` :
- `WeekReviewInput.activity?` — trois états : `[…]` lu, `[]` lu et vide, `null`/absent **pas lu** ;
- `WeekReviewReading.activity: WeekActivitySummary | null` — champ **additif**, `null` sur un gel
  antérieur, donc **pas de bump de `WEEK_REVIEW_FACTS_VERSION`** (même arbitrage, mot pour mot, que
  `evidence` de FF-009 : une version neuve rendrait illisibles tous les gels existants) ;
- `renderDeterministicWeekReview` — la phrase du fait, **avant** la question, dans **toutes** les
  branches y compris `insufficient_data` (le mouvement de la semaine ne dépend pas de la couverture
  alimentaire — c'est justement la semaine où c'est la seule chose qu'on sache) ;
- `weekReviewPromptBlock` + `describeWeekReview` — les comptes, plus trois interdits ;
- `allowedWeekNumbers` — les huit nombres du résumé, sinon une composition exacte partirait en repli ;
- `COUNTABLE` — `sessions?|workouts?|minutes?` ajoutés. **Sans ça la ceinture était aveugle** :
  « you trained 5 times » serait passé sur une semaine à 3 séances, parce qu'un nom absent de cette
  liste n'est pas *permis*, il est *jamais inspecté*.

**Zéro ne s'imprime jamais.** Ni `0 séance`, ni `null`. Un décompte à zéro se lit comme un échec, et
le dépôt a déjà payé cette phrase exacte (« 0 des 5 jours que j'ai vus »). Ici c'est pire : aucune
prescription individuelle n'existe (`MODEL.md` §3), donc zéro n'est même pas un manque.

Rendus réels :

```
activity = null       → Thanks — that's saved. I didn't see Fatty fish at all. What made that one hard?
activity = []         → Thanks — that's saved. I didn't see Fatty fish at all. What made that one hard?
1 séance              → Thanks — that's saved. You also logged 1 training session. I didn't see …
3 séances / 2 jours   → Thanks — that's saved. You also logged 3 training sessions across 2 days. I didn't see …
couverture insuff.    → Thanks — that's saved. I only have 2 days of your week on the food side, so I'll
                        leave the eating out of it this time. You also logged 3 training sessions across 3 days.
```

### 4. La ceinture d'énergie (nouvelle)

Le prompt système interdit maintenant les calories **pour une séance comme pour un repas**. Une
règle de prompt sans vérificateur est une intention — `week_review.ts` le dit lui-même — donc la
règle est adossée à un verdict : `acceptComposedWeekReview` rend
`reason: "energy_number"` quand `findNumericNutritionTarget(text) === "energy_unit"`.

Le détecteur est **celui du dépôt** (`nutrition_lexicon.ts`, testé motif par motif), pas un matcher
maison. Seul le motif `energy_unit` est branché : les trois autres visent les macros
(« 30 g de protéines ») et mordraient sur la prose des groupes alimentaires que le bilan cite par
construction (« lean protein ») — et un faux positif ici est **silencieux**, le bilan part en repli
sans que personne voie la voix du coach manquer.

La ceinture a **un cas qui passe**, testé : sans lui elle bloquerait tout en ressemblant à une
ceinture qui marche.

## Une couture connue, non gardée

La liste `kind` existe à **deux endroits** : le `CHECK` de la migration et `ACTIVITY_SESSION_KINDS`
(`activity_session.ts`). Rien ne vérifie automatiquement qu'elles restent égales — le test
`activity_session_test.ts` fige la liste TypeScript, et la migration fige la liste SQL, mais aucune
assertion ne les confronte. Les deux sont figées et le refus d'un jeton hors liste est prouvé des
deux côtés ; c'est le jour où quelqu'un en ajoutera un troisième d'un seul côté que ça mordra.
Le commentaire de colonne en base nomme les deux fichiers, dans les deux sens.
