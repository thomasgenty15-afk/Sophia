### Incident d'isolation (majeur — documenté, run relancé proprement)

Au cours du run initial sur le scope `web` partagé, la table `chat_messages` de Rose (scope `web`) s'est révélée contenir une douzaine de messages **que je n'ai jamais envoyés** (« Hey Sophia, grosse journée là… », « Coucou… soirée un peu bizarre, je tourne en rond chez… », « Ok ça redescend un peu, merci. Tiens pour anticiper… », etc.), intercalés au milieu des miens avec des timestamps à la seconde près (23:51–23:55 UTC). C'est le comportement exact d'une **seconde session QA tournant en parallèle sur le même compte Rose / scope `web`**. Conséquence directe observée : `test-send-message` charge l'historique récent par `scope` (`loadRecentDbHistory`), donc mes tours à partir de ~T3 chargeaient l'historique de l'autre session comme contexte, et le « rappel déjà existant » signalé à mon tour de rappel (T8 initial) venait de rappels créés par l'autre session. Le rapport `rose-global15-r2` avait déjà anticipé exactement ce risque et recommandé une connexion temporaire dédiée.

**Décision** (conforme guidelines « Connexions Et Isolation » + « Gestion Des Incidents » : ne pas fabriquer un succès sur un run invalide, reprendre proprement) : abandon du run `web`, nettoyage de mes effets `web`, et **relance intégrale des 15 tours sur un scope dédié isolé `qa-rose-g15-r3-iso`**. Cela isole l'historique par tour et `temp_memory`. Les tables d'effets durables (`scheduled_checkins`, `user_plan_item_entries`, `memory_items`) restent partagées par `user_id`, donc j'ai attribué mes effets par corrélation contenu + timestamp au sein de ma fenêtre de tour, et snapshoté juste avant chaque vérification. La session concurrente est restée idle (aucun nouveau message pendant ≥12 s) pendant le run isolé, ce qui a fiabilisé les vérifications DB.

**Recommandation reprise de r2** : ces runs QA doivent utiliser une connexion **et** un scope temporaires dédiés par run, jamais le compte + scope `web` persistant de `rose@gmail.com`, tant que plusieurs runs QA peuvent tourner le même jour sur le même environnement local partagé. Le fait que la contamination touche aussi `memory_items` (le memorizer est per-user, scope-agnostique — voir Tour 6) rend l'isolation par scope insuffisante à elle seule pour la mémoire.

### Incident infra (mineur, non bloquant)

Trois tours du run isolé (le premier essai de iso3, iso4, iso5 — les tours « lourds » : product_help + deux skills) ont renvoyé **HTTP 502 `{"message":"An invalid response was received from the upstream server"}`** avec réponse vide. Ledger vide à chaque fois (aucun effet durable créé, vérifié). Conformément aux guidelines (pas de fallback, reprendre au point d'arrêt), chaque tour a été **retenté une fois** et a abouti proprement en HTTP 200. Cause probable : timeout gateway local sur le chemin IA réel sous charge concurrente (l'autre session tournait). Les verdicts de tours ci-dessous portent sur les réponses valides obtenues au retry ; les 502 sont documentés mais ne changent pas le verdict fonctionnel des tours.

### Nettoyage de fin de run (autorisation explicite)

Effets créés par MON run isolé, tous restaurés : 2 `user_plan_item_entries` (iso1 `099574ea`, iso2 `2d4854f9`) supprimées ; `current_reps` des deux habitudes remis à 0 ; 1 `scheduled_checkins` (iso7 `06fcc40c`, rappel « frère » 9h15) supprimé ; 18 `memory_items` du batch de trigger memorizer (`extraction_run_id=7ac80302`, baseline pré-trigger = 0) supprimés ; ligne `user_chat_states` du scope isolé supprimée. État final vérifié : `user_plan_item_entries`=0, `memory_items`=0, `current_reps` habitudes = 0.

**Résidu non-mien laissé en place et documenté** : `scheduled_checkins` pending est passé de 3 à 7 pendant la fenêtre du run à cause de rappels créés par la **session concurrente** (`6d4c049b` 18:00, `4a48b112` 18:30, un 19:00, `e1605e47` 07-04 08:40). Ces lignes ne sont pas les miennes ; je ne les supprime pas (règle « rétablir ce qui a été changé » = mes changements uniquement), mais elles laissent Rose au-dessus de sa baseline pending documentée. À nettoyer par le propriétaire de la session concurrente.

## Verdict Global

- Verdict: **red**
- Raison principale: sur 15 tours, 7 `green`, 7 `yellow`, 1 `red`.
