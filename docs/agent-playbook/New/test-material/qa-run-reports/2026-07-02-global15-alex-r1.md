Le classifieur d'intention semble avoir capté le slot horaire/action correctement mais pas la cardinalité (une fois vs récurrent).
- Owner runtime: dispatcher / tool arbitration (product/status/tool), puis `create_recurring_reminder_tool_skill` en aval.
- Meilleure correction selon les guidelines: corriger au niveau de l'arbitration dispatcher qui distingue `one_shot_reminder` vs `recurring_reminder_tool_skill` à partir des signaux de cardinalité explicites dans le message ("tous les soirs", "chaque soir", "à chaque fois"), et faire en sorte que le texte de confirmation ne puisse jamais annoncer une récurrence tant que le tool skill récurrent n'a pas réellement committé un enregistrement `user_recurring_reminders`. C'est un contrat runtime (EffectLedger / claim-must-match-commit), pas une reformulation de phrase.
- Pourquoi ce n'est pas un patch local: une regex sur "tous les soirs" pourrait forcer un routage vers le bon tool skill dans ce cas précis, mais ne réglerait pas la garantie générale que la réponse visible ne peut annoncer un effet que si l'EffectLedger montre le commit correspondant — la classe de bug (claim sans commit adapté à la cardinalité demandée) reviendra sous d'autres formulations.

## 4. Analyse Systeme

**Verdict: red**

**Routage**
- Dispatcher globalement cohérent : `coaching_recommendation` → `plan_realignment` (Tour 4) dès que l'intention d'exécution devient explicite ; `product_help` et `feature_opportunity` correctement isolés ; safety pregate a bien fait monter `risk_band` à `low` au Tour 9 puis redescendre à `none` au Tour 10.

**Skills / Operations / Tools**
- `create_one_shot_reminder` fonctionne correctement pour une demande ponctuelle claire (Tour 5), avec effet durable vérifié en DB et recap fidèle (Tour 6).
- `create_recurring_reminder_tool_skill` n'a jamais été invoqué malgré une demande explicite de récurrence au Tour 12 : le tool always-on one-shot a été exécuté à sa place, sans slot-filling ni confirmation attendue pour un engagement récurrent.

**Memory / Effets durables**
- EffectLedger correct sur les Tours 5 et 12 en termes de comptage technique (`committed=1`), mais le texte de confirmation du Tour 12 ne correspond pas à la cardinalité réellement committée.
- Recap du Tour 14 fidèle à la DB réelle (2 occurrences), ce qui confirme que la DB elle-même est cohérente — le problème est localisé à la promesse du Tour 12, pas à la couche de projection.

**Problèmes**
- Tour 12: mauvais tool sélectionné pour une demande de récurrence explicite + confirmation d'un effet non committé. Famille: BF-ROUTE-03 / BF-LEDGER-01. Impact système: le user croit avoir un rappel permanent alors qu'il n'a qu'un rappel unique ce soir — risque direct de rupture de confiance produit et de rechute sur l'habitude ciblée. Sévérité: red.
- Tour 14: le recap n'expose pas l'écart de cardinalité créé au Tour 12. Famille: BF-LEDGER-01 (suite). Impact système: fenêtre supplémentaire où l'écart reste invisible pour le user. Sévérité: yellow.

**Fix propose**
- Source amont: arbitration dispatcher tool vs tool-skill sur la cardinalité (one-shot vs recurring) + garde finale qui interdit un texte de confirmation "récurrent" sans commit `user_recurring_reminders` correspondant.
- Correction recommandée: étendre la détection de signaux de cardinalité ("tous les soirs", "chaque soir", "à chaque fois", "tous les jours") dans l'arbitration en amont du tool always-on, pour router vers `create_recurring_reminder_tool_skill` (avec confirmation) au lieu de `create_one_shot_reminder` ; ajouter une garde côté EffectLedger/final response qui bloque toute formulation de récurrence si aucun enregistrement `user_recurring_reminders` n'a été committé dans le tour.
- Tests d'invariant attendus: test contractuel "demande contenant un marqueur de récurrence explicite ne doit jamais aboutir à `create_one_shot_reminder` seul" ; test d'intégration "toute réponse contenant une formulation de récurrence doit avoir un `user_recurring_reminders` committé dans le même tour" ; rerun QA ciblé sur `create_recurring_reminder_tool_skill` après fix.
