### Incident système (majeur) — memorizer quotidien inopérant pour Rose (`URI too long`)

En fin de run, le déclenchement standard de `trigger-memorizer-daily` (fenêtre par
défaut 30h) pour Rose échoue **de façon reproductible** en HTTP 500. L'erreur remontée
au log est `[object Object]` (l'erreur n'est pas une instance `Error`), mais le détail
capturé dans `system_error_logs` est explicite : **`URI too long`**.

Cause racine confirmée par lecture du code :
`trigger-memorizer-daily/index.ts` → `loadUnprocessedMessages` charge tous les
`chat_messages` `role=user` de l'utilisateur sur la fenêtre, puis filtre les déjà-traités
avec `.in("message_id", ids)` où `ids` = **tous** les ids de la fenêtre. Rose a **219
messages user sur 30h répartis sur 15 scopes** (accumulation de nombreux runs QA du
jour). Le `GET` PostgREST `memory_message_processing?...&message_id=in.(<219 uuids>)`
dépasse la limite de longueur d'URI → l'appel jette avant `messages_loaded`, donc **le
batch entier échoue et n'écrit aucun `memory_items`** pour Rose.

Conséquence QA directe : la vérification mémoire différée (Tour 6) ne pouvait pas passer
par le chemin nominal. Conformément aux guidelines (pas de fallback fabriqué, reprendre
proprement), j'ai relancé le **même** batch en réduisant la fenêtre via le paramètre
supporté `hours:1` (18 messages : mes 15 + 3 d'un run adjust-level concurrent), ce qui
fait passer le `.in()` sous la limite. Le batch aboutit alors en HTTP 200
(`extraction_run_id=3f9a4e8a`, 8 `memory_items` écrits) et le fait du Tour 6 est bien
persisté (voir Tour 6). Le planner/writer mémoire fonctionne donc ; **c'est le
chargement de messages du batch qui est fragile**. Classé `BF-MEMORY-01` (symptôme :
promesse mémoire non persistée via le chemin nominal ; owner : memorizer batch).

Nuance honnête : le volume de 219 messages / 15 scopes en 30h est **amplifié par
l'accumulation de données de test** (un vrai utilisateur n'a pas 15 scopes). Mais le
`.in()` non borné reste un défaut de robustesse réel qui casse pour tout utilisateur
suffisamment actif sur la fenêtre.

  `00-architecture-doctrine.md` (compréhension par JSON IA, garde-fous déterministes

  qui laisse croire à un log. Le T3 confirme que le chemin explicite fonctionne : c'est
  bien le pont implicite→durable + le surfaçage du clarify qui manquent.
- Pourquoi ce n'est pas un patch local: c'est un contrat intake + coordination
  tool-skill/réponse, pas une regex sur la formulation.

## 4. Analyse Système

**Verdict: yellow**

**Routage**
- Cohérent sur l'ensemble : `track_progress_plan_item` (T1, T3), `coaching_recommendation`
  (T4, T5), `normal_reply` (T2, T6, T9-T13, T15), `create/cancel_one_shot_reminder`
  (T7, T8, T9), `product_help` (T8, T14). Safety pregate correct : `none` au repos,
  `medium` sur rechute+culpabilité (T10) et craving aigu (T11), jamais de `safety_crisis`
  sur-déclenché.
- Frictions d'ownership : item framework nommé capté par le flow coaching actif (T5,
  `active_coaching_recommendation`). Nit de trace : `direct_effects_to_run` mal étiqueté
  (`create` au lieu de `cancel`) aux T8/T9 — métadonnée seulement, l'effet réel est
  correct.

**Skills / Operations / Tools**
- `track_progress_plan_item` : commit propre sur task (T1) et sur habitude count via
  phrasé explicite (T3). **Faille détection** : le phrasé implicite (T2) est bloqué
  `target_not_evidenced` et le `needs_clarify` n'est pas surfacé → progrès perdu sans
  question. Point yellow principal côté effet.
- `create_one_shot_reminder` / `cancel_one_shot_reminder` : cycle create (T7) → cancel
  (T9) **exécution unique et propre**, deux effets durables vérifiés en DB. Le
  `BF-LEDGER-02` (double-exécution / faux doublon) de r3 **n'est pas reproduit**.
- `coaching_recommendation` : technique adéquate (mot de bascule T4) et
  `action_context.plan_item_id: null` → l'**UUID halluciné** `BF-EFFECT-03` de r3 n'est
  pas reproduit. Mais le flow actif capte l'item framework nommé (T5).
- `product_help` : honnête et groundé (T8 mode sombre, T14 Initiatives).
- Recap projection (T13) : **branchée sur l'état plan réel** — `BF-STATUS-01` non
  reproduit.
- Safety : interprétation correcte d'une rechute passée comme `missed`/`correction`
  (T10) + blocage du write pendant safety ; classification `medium` juste sur le pic
  (T11) ; désescalade propre (T12).

**Memory / Effets durables**
- 2 `user_plan_item_entries` créées (T1, T3), 1 `scheduled_checkins` créé puis annulé
  (T7/T9) — tous vérifiés en DB puis nettoyés.
- Mémoire explicite (T6) : persistée et active **après batch memorizer** — mais
  seulement via une fenêtre réduite (`hours:1`). Le chemin nominal (30h) **échoue** :
  voir ci-dessous.
- **Incident système majeur** : `trigger-memorizer-daily` échoue en HTTP 500
  (`URI too long`) pour Rose sur la fenêtre par défaut. `loadUnprocessedMessages` filtre
  les déjà-traités par `.in("message_id", ids)` avec **tous** les ids de la fenêtre
  (219 messages / 15 scopes en 30h) → URL PostgREST trop longue → le batch jette avant
  d'écrire quoi que ce soit. Sous ce chemin, la promesse mémoire du T6 ne serait pas
  persistée pour Rose (`memory_items=0`).

**Problemes**
- Tour 2: progrès rapporté non loggé + clarify non surfacé. Famille: BF-EFFECT-02.
  Impact système: effet durable attendu absent, coordination tool-skill/réponse.
  Sévérité: yellow.
- Tour 5: item framework nommé capté par flow coaching actif. Famille: BF-ROUTE-02
  (+ BF-ROUTE-01). Sévérité: yellow.
- Incident système (transverse, découvert à la vérif mémoire): memorizer quotidien
  inopérant pour Rose (`URI too long`, `.in()` non borné). Famille: BF-MEMORY-01.
  Impact système: aucune écriture mémoire via le batch nominal pour un utilisateur
  suffisamment actif. Sévérité: yellow (réel mais amplifié par l'accumulation de
  données de test ; récupérable en bornant la fenêtre ; planner/writer sains).

**Fix propose**
- Source amont: (1) `trigger-memorizer-daily/loadUnprocessedMessages` — remplacer le
  `.in("message_id", ids)` non borné par un anti-join / RPC (`NOT EXISTS` sur
  `memory_message_processing`) ou un chunking des ids sous la limite d'URI ; (2) intake
  `track_progress` — mapping sémantique déterministe de la cible + surfaçage obligatoire
  du `needs_clarify` sur effet durable ; (3) active flow policy — prioriser un item de
  plan nommé à skill dédié sur un flow générique actif ; (4) nettoyer le nit de trace
  `direct_effects_to_run` (cancel mal étiqueté create).
- Correction recommandée: prioriser (1) `BF-MEMORY-01` (casse un sous-système durable
  entier) puis (2) `BF-EFFECT-02` (T2, perte silencieuse de progrès).
- Tests d'invariant attendus: `trigger-memorizer-daily` DOIT réussir pour un user à
  fort volume de messages sur la fenêtre (ex. ≥ 500 ids) sans erreur URI ; un rapport de
  complétion implicite DOIT commit OU poser une clarification visible ; un item de plan
  nommé à skill dédié DOIT primer sur un flow générique actif.
