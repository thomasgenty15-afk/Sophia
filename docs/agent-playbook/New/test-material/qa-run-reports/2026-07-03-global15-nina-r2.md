**Analyse**
- Symptôme: le user a créé au T6 un rappel « ce soir 22h30 » et, quelques tours plus tard (timeline simulée 21:40 Paris), Sophia répond « aucun rappel de prévu ». Du point de vue UX de la timeline simulée, c'est une **négation d'un effet durable attendu**.
- Source amont probable — **artefact d'environnement dominant**: le cron local **`process-checkins` (`*/3 * * * *`, actif)** tourne sur l'**horloge réelle serveur** (≈ 21:57 UTC réel), alors que le `scheduled_for` du rappel (20:30 UTC) dérivait du **`client_now` simulé** du soir. L'heure réelle étant postérieure au `scheduled_for`, le cron a **déclenché le rappel** → `awaiting_user` avant le recap. La réponse « aucun rappel de prévu » est donc **cohérente avec l'état DB post-fire** (plus aucun checkin *pending/futur*, 0 recurring). Ce n'est donc pas prouvé comme un bug de projection : c'est le décalage `client_now` simulé vs horloge réelle + cron temps réel qui a muté l'état pendant le run (exactement le type d'interférence que les guidelines demandent d'éviter).
- Hypothèse à écarter (BF-STATUS-01/02): si un rerun avec crons en pause / `client_now` aligné sur le temps réel montre que le recap **ignore** un checkin réellement pending pour aujourd'hui, alors ce serait un vrai bug de projection recap. À R4-T12, Alex avait bien obtenu un recap correct (« rappel à 22h30 ») quand le temps réel était antérieur au fire — ce qui appuie l'hypothèse artefact.
- Owner runtime: testabilité/environnement (cron `process-checkins` + endpoint `test-send-message` qui n'aligne pas l'horloge des crons sur `client_now`). Owner recap seulement si l'hypothèse BF-STATUS se confirme au rerun.
- Meilleure correction: (1) pour la testabilité — garantir qu'aucun cron `process-checkins` ne tourne pendant un run QA, ou aligner le `client_now` sur le temps réel serveur pour les tours qui créent des rappels datés, afin de ne pas fabriquer un `scheduled_for` déjà passé ; (2) rerun ciblé du recap crons-off pour trancher BF-STATUS.
- Pourquoi ce n'est pas un patch local: le symptôme vient d'une contamination temps-réel/simulé, pas d'un wording. Reformuler le recap ne corrigerait rien et masquerait un éventuel vrai BF-STATUS.
