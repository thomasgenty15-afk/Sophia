## 4. Le défaut que le premier tir réel a trouvé — reproduit, corrigé, rejoué

### 4.1 Ce qui s'est passé

Tir réel n° 1, requête `4d82720c` : **`422 plan_not_deliverable`**, une seule cause bloquante —

```
ingredient_not_bought « champignons de Paris »
  « champignons de Paris » n'est ni sur la liste de courses ni au garde-manger
```

…alors que la ligne **est** sur la liste, écrite au caractère près, **200 g pour 200 g**. Au même
instant, l'autre lecteur de courses annonçait l'inverse :
`shopping_rebuild { lines: 22, requantified: 22, needs_unbought: 0, unbought_terms: [] }`.

### 4.2 La mécanique

`resolveCompositionLine` rend **deux identités pour le même mot** :

| ligne | `ref` écrit | identité obtenue |
|---|---|---|
| ingrédient de `prep_frittata` | `button_mushroom_cultivated_mushroom` (écrit par **le modèle**) | `button_mushroom_cultivated_mushroom` |
| ligne de courses | *aucun* → résolu par le **libellé** | `champignons_de_paris` (entrée du sas) |

La base d'alias porte « champignon de paris ou champignon de couche cru » et « champignons » —
**pas** « champignons de paris ». Le libellé atteint donc l'entrée du sas, pas le slug du modèle.

`final_plan_audit.ts` possède exactement le pont qu'il faut (`identityByTerm`, égalité EXACTE de
termes normalisés) — mais il ne le franchissait que si `ref === null`. **C3 a donné un `ref` aux
lignes de courses dans le même lot** (`meal_generation.ts`, projection `shopping_list` :
`resolveCompositionLine(index, { term, ref: null })`). Ce `ref` n'est pas un identifiant du
modèle, c'est le **libellé résolu** — et il désarmait le pont écrit pour ce cas précis. Le
commentaire du bloc disait encore « LES LIGNES DE COURSES N'ONT AUCUN IDENTIFIANT AUJOURD'HUI » :
il était périmé par son propre lot.

### 4.3 La correction

`final_plan_audit.ts` applique désormais **la règle de `rebuildShoppingQuantities`, mot pour
mot** : « le pont ne sert que lorsque la ligne n'atteint aucun besoin ; il ne peut donc pas
détourner une ligne qui en atteignait un. » Les deux lecteurs appliquent la même condition, donc
ils ne peuvent plus rendre deux verdicts opposés sur le même plan.

```ts
const directIdentity = foodIdentityOf(index, { term, ref, refRefused }).identity;
const declared = !refRefused && !needIdentities.has(directIdentity)
  ? identityByTerm.get(normalizeTerm(term)) ?? null
  : null;
```

`needIdentities` est figé **avant** la boucle d'achat : le lire dans `acc` pendant la boucle
ferait dépendre le pont de l'ordre des lignes de courses.

### 4.4 La preuve, à coût nul

`banc-lot-F.ts` reçoit un drapeau `--reponse=<sortie d'un tir>` qui repasse une réponse réelle
dans le **vrai handler** sans repayer l'appel.

| | commande | résultat |
|---|---|---|
| **avant** | `perte --reponse=campagne-tir1-c6-….json --compte=c6repro1` | **422 `plan_not_deliverable`**, `ingredient_not_bought « champignons de Paris »` aux rounds 0, 1 et 2 · 0 ligne écrite |
| **après** | le même, `--compte=c6repro2` | **200**, plan `2c7fbe3b` écrit · `final_gate ok=true · refus 1 · bloquants 0 · causes ["cell_energy_off"]` |

**Régression épinglée** — `shopping_c3_test.ts` §⑩, deux épreuves, l'une qui passe et l'autre qui
mord :

- « une ligne dont le `ref` vient de son LIBELLÉ rejoint le besoin du modèle » — l'audit rend
  `covered_measured`, `boughtRawG: 200`, **0 `not_bought`**, et `rebuildShoppingQuantities` rend
  `needs_unbought: 0` : les deux lecteurs disent la même chose ;
- « LE CAS QUI MORD : un `ref` qui atteint DÉJÀ un besoin n'est pas détourné » — deux besoins
  portent le même libellé ; la ligne reste sur l'identité qu'elle déclare et l'autre besoin reste
  `not_bought`.

⚠️ **Le tir n° 1 reste un échec dans le tableau de campagne.** Il n'est pas remplacé par un vert :
il est refusé, sa cause est trouvée, corrigée, et la **même réponse** est livrée après correctif.
Le tir payant de confirmation n'a pas été passé — le budget de six appels était épuisé.
