## 4. Rapport fluidite humaine

Verdict : red.

La conversation n'est pas suffisamment humaine.

Problemes principaux :

- 11 tours sur 20 sont des reponses vides avec `aborted=true`.
- Les tours 3 et 4 repetent exactement la meme reponse.
- Plusieurs reponses parlent d'un autre contexte : envoi, telephone, excuse, parole seche, lien blesse.
- Sophia ne suit pas la trajectoire emotionnelle : elle passe trop tot en execution, puis rate la stabilisation.
- Quand l'utilisateur dit "pas maintenant" et demande l'apaisement, Sophia reste bloquee dans une operation produit.
- Le ton peut etre bon localement au tour 6, mais il n'est pas ancre dans les faits donnes par l'utilisateur.

Corrections proposees cote conversation :

- `emotional_repair` doit prioriser les signaux "je me parle mal", "incapable", "degoute de moi", "honte" avant `execution_breakdown`.
- Le generateur doit etre contraint a citer ou utiliser le contexte courant minimal avant toute suggestion.
- Ajouter une garde anti-repetition : si la reponse precedente est identique ou quasi identique, regenerer ou forcer une formulation differente.
- Ajouter une regle de sortie operationnelle : "pas maintenant", "je veux juste rester sur l'apaisement", "je ne veux pas de plan" annulent ou suspendent l'operation active.
- Pour `emotional_repair`, favoriser une sequence : validation courte -> defusion identitaire -> une question douce ou une micro-ouverture, sans plan tant que la honte domine.
- Pour une demande produit de type "c'est quoi X", `product_help` doit expliquer avant toute tool skill.

## 5. Rapport systeme

Verdict : red.

Elements systeme observes :

- `test-send-message` retourne HTTP 200 avec `ok=true` meme quand `response.aborted=true` et `content=""`.
- Les tours abortes n'ont aucune `conversation_turn_trace`, donc impossible de diagnostiquer via le contrat attendu.
- Le debounce semble provoquer des faux aborts. Le code attend 3500 ms puis annule si le message courant n'est plus le dernier message user ; pour un endpoint QA, ce comportement rend les runs longs instables.
- Les tool skills sont trop sticky : `prepare_attack_card` reste actif de T16 a T20 malgre "pas maintenant", honte, safety clarification, demande memoire et demande de phrase.
- Les tools ne passent jamais en execution success dans ce run. Le rappel T14/T15 ne cree aucune operation observable. `prepare_attack_card` reste `blocked` puis `pending_confirmation`.
- La demande memoire explicite T19 ne produit aucun memory candidate.
- Observability partielle : les traces utiles existent sur certains tours, mais les aborted turns sont invisibles hors raw response.

Corrections proposees cote systeme :

- Ajouter un mode QA a `test-send-message` : `debounce_wait_ms=0` ou `disable_debounce=true`.
- Si `aborted=true`, retourner un status non ambigu pour QA ou au minimum un champ `abort_reason`, `logged_message_id`, `latest_message_id`.
- Ecrire une `conversation_turn_trace` meme pour un abort, avec `response_owner=null`, `abort_reason=debounce`.
- Dans le routeur operationnel, traiter explicitement les intents `cancel`, `not_now`, `topic_change`, `emotional_return` pour nettoyer `__active_tool_skill_intake`.
- Dans le dispatcher, distinguer `product_question` de `tool_skill_intent_start` pour les formulations "c'est quoi / comment ca marche / a quoi sert".
- Ajouter une assertion de non-repetition dans le harness QA long.
- Ajouter une assertion "no empty response" obligatoire pour tous les endpoints conversationnels.
- Verifier le path one-shot reminder ou recurring reminder sur une demande "rappelle-moi ce soir a 18h..." avec trace attendue.
- Verifier le memorizer sur preference explicite non sensible : "quand je rate le matin, j'ai besoin..." devrait produire un candidate de type preference/statement, pas un fact identitaire.
